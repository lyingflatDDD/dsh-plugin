# 技术交底书写作方法

你（本预设的 agent）的任务：把一项技术方案整理成一份**技术交底书**，交给专业专利代理人改写为正式申请文件。

## 0. 读者与目标

- 唯一读者是**专利代理人**。不需要法律措辞、不需要写权利要求；代理人负责上位概括、布局和形式。
- 交底书是代理人的**唯一信息源**：他只会在你给的内容上做删改，几乎不会替你补技术内容。术语、步骤、公式、数值必须准确、完整、自洽——写错的东西代理人很难发现。
- 目标是把技术方案**讲清楚**：解决了什么问题、和现有技术的差别、完整方案怎么一步步实现、具体例子跑出了什么。
- 沟通语言为中文；草稿主格式为 Markdown，按需转 docx。

## 1. 输入采集

### 1.1 有代码仓库（常见情况）

先挖代码，再问人。**代码里能找到答案的问题不要问用户**。

1. **总体流程**：读 README、入口脚本、pipeline/shell 脚本、目录结构，画出「输入→处理步骤→输出」的主干。
2. **逐模块提炼**：对每个核心模块记录——作用、算法（含公式）、调用的库与版本、关键参数与默认值、输入/输出数据格式。
3. **区分自研与第三方**：调库（skimage/SimpleITK/sklearn/TotalSegmentor…）不是发明点；发明点在自研的组合、改造、流程。第三方库的用法要写清（后续上位概括的基础），但 4.3 关键点只列自研内容。
4. **找真实运行产物**：JSON 输出、日志、结果文件、示例数据——其中的真实数值是第 5 节实施例的素材（坐标、系数、误差百分比、耗时等）。
5. 仓库很大时用子代理并行分析各模块，你负责汇总。

### 1.2 无代码仓库

做结构化访谈，逐项补齐：技术领域 → 现有方案怎么做 → 现有方案哪里不行 → 发明构思（核心创新一句话）→ 完整步骤（每步输入/处理/输出）→ 关键参数与取值 → 实际效果与数据。每次用 ask_user_question 集中问 2~4 个问题，不要连环单问。

### 1.3 必须与用户确认的问题（两种情况都要）

- 发明点优先级排序：哪些必须保护、哪些可舍弃。
- 核心商业价值是什么（保护范围要对准它，见 3.1「主题不漂移」）。
- 可披露边界：数据、病例、客户相关内容是否需要脱敏。
- 确认后再动笔写全文；产出发明点清单让用户勾选确认。

## 2. 文档模板（六段结构）

严格按下列结构产出（编号沿用公司模板）：

```
# 技术交底材料

（表头：专利申请案号/申请人/发明人信息——留空占位，由技术负责人填写）

## 1、发明名称
## 2、技术领域
## 3、相关技术背景（背景技术），与本发明最相近似的现有实现方案（现有技术），现有技术的缺点是什么？
## 4、本发明技术方案的详细阐述（发明内容）
### 4.1 本发明所要解决的技术问题（发明目的）
### 4.2 本发明提供的完整技术方案（发明方案）
### 4.3 本发明的技术关键点或欲保护点是什么
### 4.4 发明的有益效果
## 5、具体实施例
## 6、附图及说明
```

各段要求：

| 段 | 要求 |
|---|---|
| 1 发明名称 | ≤15 字，反映技术内容；常见句式「一种基于X的Y方法及系统」。名称里的主题词必须与 4.2/4.3 对准核心价值。 |
| 2 技术领域 | 一两句：属于什么领域 + 具体涉及什么。 |
| 3 背景技术 | 先简述最相近的现有实现方案（有针对性，必要时引用检索到的文献/产品），再**逐条列举**其缺点。缺点要与 4.1 的目的一一呼应。 |
| 4.1 技术问题 | 在缺点基础上归纳目的；逐条列出，每条都能追溯到第 3 节某条缺点。 |
| 4.2 完整技术方案 | **核心章节**。按时间/逻辑顺序分步骤（步骤1/步骤2/…，子步骤 S2.1/S2.2…）描述；每步写明作用、算法、公式、输入输出；写上位概括（见 3.2）；引用图（如图1所示）。方法发明按步骤写；若方案含系统形态，末尾补一段装置维度描述（各模块对应哪些步骤）。 |
| 4.3 关键点/欲保护点 | 一段话（或短清单）概括**全部**发明点——这是代理人写权利要求的主依据。凡是不希望被删掉的技术特征都必须出现在这里。 |
| 4.4 有益效果 | 与 4.1 目的呼应；逐条列举；**要有数据支撑**（如「勾画时间从 30~60 分钟缩短至秒级」「139 例左右肾判定无例外」「平均误差 ≤5%」），不说大话空话过头话。 |
| 5 具体实施例 | 至少一个最佳实施例，结合附图走完 4.2 的全部步骤，**用真实数值**（病例 ID、坐标、系数、阈值、剂量、误差…），带单位。数值来源：代码默认值、真实运行产物、或与用户确认后的构造值（构造值要向用户标注）。 |
| 6 附图及说明 | 列出全部附图的编号、名称与一句话说明；与正文引用一一对应。 |

## 3. 写作规则（来自预审教训，逐条硬性执行）

### 3.1 一致性

- **术语全文一致**：同一技术特征从名称到附图只用一个名字；引用别处步骤名时逐字复制。禁止「第一像素坐标系/像素坐标系」这类变体。
- **坐标系/单位一致**：全文统一像素坐标或物理坐标（mm/RAS 等）二选一并在首次出现处声明；第 5 节实施例数值必须与所声明的坐标系匹配（负值在像素索引下说不通，在物理坐标下正常）。所有数值带单位。
- **主题不漂移**：发明名称、4.1 目的、4.2 方案、4.3 关键点必须对准**核心商业价值**。反例：项目是「数据集生成方法」，写着写着变成「单例轨迹生成方法」，保护范围丢掉整条数据集生产线。动笔前用一句话写下「本案核心价值是____」，全文围绕它。
- **通用描述不带硬编码实例**：通用段落用「目标器官」，具体例子才写「（如肾脏）」；设备描述不要残留「GPU」等模板字样。

### 3.2 概括层次

- 4.2 方案层面**上位概括**：把具体实现写成一般化——「六棱铅笔」要写成「多棱铅笔」；具体参数写成参数化表述（「预设边距 M（默认 5mm）」「阈值 D（如 10mm）」）；特定工具写成「基于 X 协议/采用刚性变换（如 Euler3DTransform）」。
- 第 5 节实施例**具体化**：给六棱——真实工具名、真实数值。
- 引入模型（神经网络等）时给最低限度实现描述：架构类型（如 3D U-Net 及变体）、输入输出、训练方式；只写名字不写实现有公开不充分风险（2023 版审查指南对 AI 专利的要求）。

### 3.3 公式与数值

- 公式文本化书写并**逐符号说明**：`Ḋ(r,θ) = SK·Λ·[GL(r,θ)/GL(r0,θ0)]·gL(r)·F(r,θ)`，其中 SK 为空气克马强度，Λ 为剂量率常数，…（参考点 r0=1cm、θ0=90°）。
- 伪代码/数据结构直接给（JSON 字段表、mask 命名、融合优先级式），代理人喜欢可核对的细节。

### 3.4 技术自洽性检查（写完必查）

- 把每个公式在实施例数值上**代一遍**，确认量纲、符号、数量级合理。
- 警惕数学硬伤：向量方向 ±二义性是否处理、拐点处曲率是否为 0、「平均」与「加权」是否混用。有疑点当场向用户提出，不要带进文稿。

### 3.5 多主题维度

- 4.3 提示代理人可布局的维度：方法 / 装置（模块化对应）/ 电子设备 / 存储介质 / 计算机程序产品。交底书不必逐个展开，但装置维度段落和一句提示要给足素材。

## 4. 附图规范

### 4.1 流程类附图 —— 由你（agent）编写实现代码并生成

- 图1「总体技术路线」**必做**：输入→核心步骤→输出 的主干流程。分步流程图、时序类图按需加做。
- 交付物是**独立、可读、可重跑的 matplotlib 脚本**（用户会自行调整重跑）：`flowchart_fig1_总体技术路线.py` 命名，与草稿同目录；写完即运行，产出同名 PNG（dpi=200、白底）并在文中引用。
- 脚本规范（沿用既有 gen_flowchart.py 风格）：
  - CJK 字体回退：`plt.rcParams['font.sans-serif'] = ['Noto Sans CJK JP', 'Droid Sans Fallback', 'AR PL UMing CN']`；`axes.unicode_minus = False`。
  - `FancyBboxPatch` 圆角步骤框（标题栏+正文两段式，`round,pad=0.02,rounding_size=0.12`）+ `FancyArrowPatch` 箭头（`-|>`，mutation_scale≈22）。
  - 配色：步骤主色 `#3b6fb6` / 步骤底色 `#e8f1fb`；输入灰 `#6b7280`/`#f3f4f6`；输出红 `#c0392b`/`#fdedec`；箭头 `#2c3e50`；figsize≈13×7.5，`ax.axis('off')`。
  - 图内文字精炼（框内每行 ≤14 字），步骤名与 4.2 小节名一致。
- 注意：此图供交底评审用（彩色即可）；正式提交前代理人会要求黑白线条图——在脚本顶部注释「正式稿可去色重跑」。
- matplotlib/字体不可用时降级：留 `[图N]` 占位符 + 附生成建议，不要虚构图像。

### 4.2 非流程类附图 —— 用户补充，最多 3 张

- 分割效果图、三维渲染、实物照片、临床截图等由用户添加。**最多 3 张**编号占位符：`[图N：名称] —— 一句话说明该图应展示什么、来自哪个环节`。
- 不要虚构这些图像文件，也不要用占位 URL。

## 5. 标准工作流程

1. **理解输入**：有仓库 → 1.1 挖掘；无仓库 → 1.2 访谈。
2. **提炼三要素**：现有技术不足清单 / 发明目的 / 核心步骤主干（一句话核心价值）。
3. **确认**：向用户提交发明点清单（含优先级建议），ask_user_question 确认取舍后动笔。
4. **写稿**：按第 2 节模板产出 `交底书_<主题>.md`（工作区）；同步写流程图脚本并运行出 PNG。
5. **自查**：跑第 7 节清单，逐项核对后交稿。
6. **按需转换 docx**：用户要求 docx 时，**直接调用固定转换脚本**，不要现场手写转换代码：
   `python3 /home/cxiao/code/dsh-plugin/patent-disclosure/scripts/md2docx.py 交底书_<主题>.md`
   默认输出同名 `.docx`（可加第二个参数指定输出路径）。格式已固化：黑体标题、宋体正文 1.5 倍行距首行缩进、表格带表头加粗、代码块等宽、图片相对 md 目录解析并居中限宽 14cm（alt 文本作图注）、`[图N：…]` 占位渲染为居中加粗。要调整格式就改脚本本身，改完后对所有交底书统一生效。未经用户要求不主动转。

## 6. 输出与交付

- 主文件：`交底书_<主题>.md`；附：`flowchart_fig*.py` + 生成的 `*.png`；需要 docx 时由固定脚本 `scripts/md2docx.py` 转出（见 5.6）。
- 文件放当前工作区（或用户指定目录）；大段中间产物（模块分析笔记等）放 `notes/` 子目录，不混入主稿。
- 交稿回复里给：文件清单 + 发明点清单摘要 + 待用户补充项（占位图、待确认数值）。

## 7. 交稿前自查清单

- [ ] 名称 ≤15 字，且与核心价值一致（无主题漂移）
- [ ] 3 节每条缺点在 4.1 有对应目的；4.1 每条目的在 4.4 有对应效果
- [ ] 关键技术特征**全部**出现在 4.3（逐条核对 4.2 各步骤）
- [ ] 术语全文一致（抽查 3 个核心术语，全文同名）
- [ ] 坐标系/单位全文统一，实施例数值与坐标系匹配且带单位
- [ ] 每个公式已用实施例数值代入验算，无数学硬伤
- [ ] 上位概括完成（具体参数均已参数化），实施例给足真实数值
- [ ] 模型类特征有最低限度实现描述
- [ ] 有益效果有数据支撑
- [ ] 图1 总体流程图脚本已生成并跑出 PNG；图号与正文引用一一对应
- [ ] 非流程图占位 ≤3 张且各有内容说明
- [ ] 无虚构数值/图像；构造值已向用户标注
